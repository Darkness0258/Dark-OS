- [~] Store / Packages / Updates / Games — `darkos-store.py` provides read-only Search/Installed/Updates/Compatibility tabs. **2026-09-06 fixes:** work runs outside GTK with bounded, coalesced requests; stale callbacks are ignored; nonzero command exits and AUR RPC errors stay visible; status no longer executes Proton. Eight regressions and real GTK startup pass. **2026-09-06 (cont'd) — pacman installs now gated, not just disabled:** new `darkos-store-gated-install.py` resolves a package's download targets via `pacman -Sp`, downloads without installing (`pacman -Sw`), scans every resolved file with Shield's `scan_path` (the same function Security's Shield tab uses), and only then installs (`pacman -U`) — a resolution mismatch, a download failure, or any non-clean scan result makes `-U` unreachable, checked directly in tests. Store's pacman Install buttons call it (behind a confirm dialog) via the same `sudo`-inside-a-visible-`the-void.sh`-terminal handoff Security's "Update Definitions" button already uses — one password prompt, and the user watches the whole download/scan/install happen. The button only enables when `clamscan` is actually present (`shutil.which`); otherwise it stays disabled with the original message, same fail-closed rule as Shield itself. AUR and Flatpak are excluded from *this* gate, not forgotten — the AUR build step (`makepkg`) executes arbitrary shell from the PKGBUILD, so scanning the built artifact after the fact doesn't cover the actual risk the way it does for a pre-built pacman binary package. 22 new orchestration regressions pass (`ci/test-store-gated-install.py`, mocked pacman/scan calls, run fresh this session), and all 21 native apps including the edited Store still realize under Xvfb. **Not verified:** any of this against a real pacman transaction — no Arch root shell was reachable this session (Docker blocked on the Windows host, see ci/phase-7-audit.md), so the `pacman -Sp`/`-Sw` output-format assumptions are a source-review judgment call, not something run for real. Phase 6's installation goal is met for pacman at the orchestration-logic level; closing it fully still needs one real gated install on a live Arch box. **2026-09-06 (cont'd again) — AUR gate added, weaker by design and says so:** new `darkos-store-gated-aur-install.py` clones the package's AUR git repo as the invoking (non-root — makepkg refuses root outright) user, prints the actual PKGBUILD and requires an explicit `y` before building anything, runs `makepkg`, resolves the produced file(s) via `makepkg --packagelist`, scans them with the same `scan_path`, and only then runs `sudo pacman -U` — the one step that needs a password, asked for at that point, not upfront. Declining the PKGBUILD review, a build failure, a resolution mismatch, or a non-clean scan all make `-U` unreachable, checked directly in tests (28 new cases, `ci/test-store-gated-aur-install.py`, all pass). The confirm dialog and terminal output both say plainly that this is a materially weaker guarantee than the pacman path — PKGBUILD review by the human is the real mitigation here, not the post-build scan, since a malicious build step can already do damage before there's a file to scan. `_search_pacman`/`_search_aur`/`_search_flatpak` were also fixed to return `(id, display)` tuples instead of a single decorated string — the AUR display string ("name — description") was previously the *only* thing kept, which would have made the real package name unrecoverable for cloning; Flatpak was normalized the same way for consistency even though its Install button stays disabled (`flatpak install --no-deploy`'s on-disk layout wasn't verified this session, so it's still genuinely deferred, not just excluded on principle like AUR). Re-ran the full native-apps Xvfb suite again after these changes — still 21/21. Phase 6's installation goal now covers pacman and AUR, each honest about what it does and doesn't guarantee; Flatpak remains the one install path with no gate design yet. **2026-09-06 (cont'd, 4th) — Flatpak wired too, deliberately without a Shield scan:** `_install_flatpak` runs `flatpak install --user --noninteractive -y -- <app-id>` in a background thread (no terminal handoff needed — `--user` scope needs no root, so there's no password prompt to show). The confirm dialog states plainly why this differs from pacman/AUR: Flatpak already verifies the download's signature against the configured remote and runs the app sandboxed at runtime, which is a different protection model than a pre-install file scan, not a gap being papered over. A real Shield scan for Flatpak would mean checking out its OSTree-stored, not-yet-deployed commit into a scannable directory (`flatpak install --no-deploy` + `ostree checkout`) — the exact repo path and ref-naming mechanics weren't verified this session, so building that blind risked shipping something that silently doesn't work; deferred rather than guessed at. `_search_flatpak` and `_search_aur` now both expose `(id, display)` so the install call always has the real identifier, not the decorated search-result text. 4 new tests (`ci/test-store.py`, now 16/16) check the exact `flatpak install` argv and that a failure surfaces rather than getting swallowed; full 21-app Xvfb pass repeated once more, still clean. All three Store backends now have a real install path with a stated, technically-grounded reason for the protection model each one uses.
